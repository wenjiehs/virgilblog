# 给 Agent 做一张不自由的网：TKE CNI + ZeroProxy Demo 复盘

这几天我在做一个有点“反直觉”的网络 demo。

传统容器网络的目标，通常是让 Pod 拥有一套正常、稳定、可被服务发现和访问的网络能力。IP 要分配，路由要通，Service 要能转发，Pod 之间要能按策略互通。

但 Agent 场景里，我越来越觉得这个默认假设需要被重新拆开。

很多 Agent Pod 并不是一个长期运行的微服务。它更像一次任务执行环境：短命、动态、会运行模型生成的代码、会访问 Git、包源、内部 API、向量库、对象存储，甚至可能误访问一些不该访问的系统。

这类 Pod 最需要的不是“自由联网”，而是“被严格收口的联网”。

所以这次 demo 的目标很简单：做一张 **不自由的 Agent 网络**。

## 一开始的想法：CNI 不负责判断，只负责收口

最初我脑子里有个很容易混在一起的设计：CNI 做网络，ZeroProxy 也做网络，那它们到底怎么分工？

后来在 demo 里把边界拆得很清楚：

- **CNI 负责基础网络栈**：给 Pod 创建 netns、veth、bridge、fake IP、默认路由。
- **CNI 负责默认零互通**：Pod 不默认被访问，也不默认能直接访问其他 Agent Pod。
- **CNI 负责流量收敛**：把 Pod 出来的 TCP 流量导到 ZeroProxy。
- **ZeroProxy 负责治理**：允许、拒绝、凭证注入、审计。

这个边界很重要。

如果 CNI 既做 IPAM，又做策略，又做凭证，又做审计，很快就会变成一个既复杂又难维护的“大而全网络组件”。但 Agent 网络真正难的地方，其实不是“怎么给 Pod 一个网卡”，而是“这个 Agent 到底能访问什么、凭证怎么安全给、事后怎么追踪”。

这些都更适合放到代理层。

所以这次我给 CNI 定了一个比较克制的角色：**它只负责把流量送到治理点面前，不负责替治理点做判断。**

## 为什么 fake IP 反而合理

普通业务 Pod 的 IP 往往要进入某个稳定网络模型里。它可能要被 Service 选中，要被其他 Pod 调用，要接入 VPC 或者 Overlay 网络。

但很多 Agent 执行体没有这个诉求。

一个 Coding Agent Pod 跑完一次任务就销毁。它不需要被外部主动访问，也不应该被其他 Pod 直接访问。它需要的是：

1. 有一个基本协议栈，让程序可以正常发起请求。
2. 有一个身份和会话上下文，让策略知道“是谁在访问”。
3. 所有访问都经过治理层。

这时 IP 就不再是权限锚点，而只是一个临时网络坐标。

在 demo 里，我让 Agent Pod 使用类似 `169.254.x.x` 的 fake IP。这个 IP 不追求进入 VPC，也不承诺跨节点可路由。它的意义只是：让容器里有一个看起来正常的网络栈，然后把所有真正的访问控制交给 ZeroProxy。

这和传统 Pod 网络的直觉不太一样。

传统网络会问：“这个 IP 能不能被访问？”

Agent 网络更应该问：“这个身份、这个任务、这个 Workspace，能不能访问这个目标？”

## 真实 CNI 比 mock 更有说服力

一开始 demo 里有一层 mock，用 Python 模拟 CNI 分配 fake IP、ZeroProxy allow/deny、凭证注入。这对表达产品概念有用，但很容易被质疑：这到底是不是网络能力，还是只是应用层写了几个事件？

所以后面我把它推进到真实集群里跑。

这次 CNI 做了几件真实的事：

- 把 `agent-cni` 安装到节点的 CNI bin 目录。
- 写入新的 CNI 配置，让后续新 Pod 真的走这个插件。
- 创建 bridge 和 veth pair。
- 给 Pod 配 fake IP 和默认路由。
- 在节点上加重定向规则，把来自 Agent bridge 的 TCP 流量导到 ZeroProxy。

这一步很关键。因为只有真实替换 CNI 后，demo 才不再是“我们假装 Pod 有 fake IP”，而是“新 Pod 创建时真的经过了这套 CNI 逻辑”。

当然，这还是 PoC，不是生产级 CNI。比如 IPAM 现在还很简单，重定向也主要用规则验证路径，离规模化、灰度、回滚、可观测还有距离。

但它证明了一件事：**Agent 网络可以不是传统 Pod 网络的一个 Profile，而可以是一种新的执行体网络模式。**

## ZeroProxy 做的不是“转发”，而是治理

ZeroProxy 这层最容易被低估。

如果只把它理解成一个 HTTP 代理，那它看起来并不新鲜。但在 Agent 场景里，它承担的是网络边界里的“判断点”。

这次 demo 里，我做了几个用例。

第一个是 Coding Agent：

- 访问公开代码仓库：允许。
- 访问 repo token broker：允许，并注入 repo token。
- 访问生产数据库：拒绝。

第二个是 RAG Agent：

- 访问对象存储：允许。
- 访问向量数据库：允许，并注入 rag token。
- 访问客户敏感数据库：拒绝。

第三个是 Gateway：

- `alice` 调用 Agent：允许。
- `bob` 调用 Agent：拒绝。

第四个是绕过验证：

- 另一个 Pod 尝试直连 Agent fake IP。
- 流量被 CNI 收敛到 ZeroProxy。
- ZeroProxy 拒绝这次访问。

这里最让我觉得有价值的，是凭证注入的验证。

如果只是 ZeroProxy 日志里写一句“我注入了凭证”，其实还不够。真正要验证的是：上游服务有没有收到对应的 `Authorization` header。

所以 demo 里放了一个受保护 upstream，它会检查请求头。最后看到 upstream 返回确认事件，才说明凭证真的不是停留在日志层，而是进入了实际 HTTP 请求。

## 这个设计解决的不是 Sandbox，而是通用 Agent

中间有个认知调整也挺重要。

一开始我很容易把这个方向讲成“Sandbox 网络”。因为最典型的场景确实是工具沙箱、代码执行、浏览器环境、一次性任务。

但如果只讲 Sandbox，会把问题讲窄。

Agent 系统里至少有几类不同网络角色：

- 工具执行体：默认零互通，纯出向，短命。
- Agent Runtime：会被调用，有会话，有长连接。
- MCP Server / Gateway：天然要提供入口。
- Agent-to-Agent：需要东西向身份和调用链。
- LLM / RAG / 向量库：常驻依赖，访问频繁。

这几类角色的网络画像完全不同。不能用一套“默认零互通”去覆盖所有 Agent 角色，也不能用普通 Service Mesh 去解释所有短命执行体。

所以现在更合理的说法是：

> **Agent CNI + ZeroProxy 主要解决执行体层网络：短命、默认零互通、纯出向、需要凭证和审计的那一层。**

至于 Agent Runtime、MCP Gateway、A2A，更像是另一层 Agent 服务网格的问题。

这两个方向应该共用同一套 workload identity，但不要混在一个组件里做。

## 产品上真正要沉淀的是两个需求

做完 demo 后，我把它拆成了两个产品需求。

第一个是 **TKE Agent CNI**。

它的产品目标不是“让 Pod 网络更强”，而是：

- fake IP，不占 VPC Pod IP。
- 默认零入向、零东西向。
- Agent Pod 创建时快速建立最小网络栈。
- 所有进出路径收敛到治理层。
- 支持安装、回滚、诊断和节点池灰度。

第二个是 **TKE 集成 ZeroProxy**。

它的产品目标是：

- egress allow/deny。
- ingress caller 到 Agent 的授权。
- 凭证按策略注入，而不是放进容器。
- 审计每次访问。
- 与 TKE 的 Secret、KMS、CAM、CLS、控制台策略配置集成。

这两个需求合在一起，才是比较完整的 “TKE Infra 升级 - 网络”。

如果只做 CNI，没有 ZeroProxy，最多是一个奇怪的 fake IP 网络。

如果只做 ZeroProxy，没有 CNI，Agent 仍然可能绕过代理，网络边界不够硬。

两个放在一起，才形成了比较清楚的分工：**CNI 做收口，ZeroProxy 做判断。**

## 这次 demo 也暴露了一些现实问题

这个 PoC 跑通以后，我反而更清楚它离产品化还有多远。

第一，CNI 替换是高风险动作。

空集群里可以比较大胆地替换 CNI，但存量集群就不能这么做。产品化时更合理的路径，应该是独立 Agent 节点池、灰度启用、明确回滚，而不是全集群一刀切。

第二，IPAM 现在还太简单。

真正的 Agent 场景会有高并发、短生命周期、IP 快速复用。IP 不能成为权限锚点，身份必须来自 ServiceAccount、Workspace、任务上下文，最好能对齐 SPIFFE 这类标准身份。

第三，代理性能需要验证。

全量出向经过 ZeroProxy，在 PoC 里没问题。但真实场景里，包源、Git、大文件、向量检索、模型依赖访问都可能带来压力。什么时候全量 L7 代理，什么时候允许更轻的路径，需要后续做基准。

第四，控制台体验很重要。

如果最后让用户写一堆底层规则，这个能力很难被用起来。更好的体验应该是“来源、目标、动作、凭证、审计”五个维度：

- 谁在访问？
- 访问哪里？
- 允许还是拒绝？
- 要不要注入凭证？
- 审计到哪里？

这才是产品经理能解释、客户也能理解的形态。

## 我自己的收获

这次最有意思的点，是我对“网络能力”的理解变了一点。

以前讲网络，总会下意识追求更通、更快、更灵活。但 Agent 场景里，网络能力的价值不一定是“更自由”，而可能是“更可控”。

一个运行模型生成代码的 Agent，不应该天然拥有完整网络访问能力。

它应该像拿到一张临时工作证：可以去指定的门，能拿指定的钥匙，所有动作都被记录，任务结束后身份和权限一起回收。

CNI 是门禁通道，ZeroProxy 是保安和钥匙柜。

这个比喻不严谨，但对产品设计挺有帮助：不要把所有东西塞到一层里。通道、判断、凭证、审计，各自有清楚的位置，系统才不会越做越乱。

## 总结

这次 demo 最后验证了一个小闭环：

1. Agent Pod 可以用 fake IP，不占 VPC IP。
2. Pod 间默认不互通，直连会被收敛到治理层。
3. 出向访问统一经过 ZeroProxy。
4. ZeroProxy 可以 allow、deny、注入凭证、记录审计。
5. 凭证注入不是日志自嗨，而是 upstream 真的收到 header。

它还不是一个产品，但已经足够支撑下一步产品需求设计。

对我来说，这次最大的判断是：

> Agent 网络不是普通容器网络的“安全增强版”，而是一种新的执行体网络边界。它不追求默认互通，而追求默认收敛；不以 IP 为中心，而以身份、任务和凭证为中心。

这件事如果能产品化，TKE 在 Agent 执行面上就不只是提供算力和 Pod，而是在提供一套更完整的基础设施边界。
