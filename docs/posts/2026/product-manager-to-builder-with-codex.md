# 产品经理不能只写方案：我借助 Codex，把一套 Agent Runtime Demo 真正跑了起来

这次项目开始时，我其实只想整理一套 Agent Runtime 方案。

目标不复杂：把隔离运行时、持久工作区和受控网络组合起来，看看能不能支撑 Coding Agent、Claw 类 Agent 这类真实场景。

如果按照我过去比较熟悉的产品工作方式，这件事很可能会变成一份完整的方案文档：有背景、有架构、有场景、有竞品、有路线图，最后再列一页“后续需要技术验证”。

但这一次，我不想停在那里。

我希望最后交付的不是“看起来可以”，而是一个真的在 Kubernetes 集群里运行过、故障过、恢复过、测量过，也暴露出明确问题的 Demo。

于是我借助 Codex，开始把自己从一个方案定义者，往构建者的位置推了一步。

## 产品经理为什么不能只停在“我想清楚了”

产品经理很容易把“想清楚”当成工作的终点。

我们擅长拆问题、画架构、定义场景、判断优先级。面对一个 Agent 基础设施问题，我很快可以把它分成三层：

- Runtime：Agent 会运行模型生成的代码，需要比普通容器更强的隔离。
- Workspace：Agent 会修改代码、安装依赖、积累状态，需要可以恢复的工作区。
- Network：Agent 会访问 Git、包源、内部 API 和数据库，需要默认收口、按目标授权和凭证治理。

这套逻辑在纸面上很顺。

但只要开始动手，很多“已经想清楚”的东西马上就会变得不确定：

- 这些组件在同一个节点上真的兼容吗？
- 为了安装运行时，需要改多少宿主机配置？
- 节点坏了以后，是组件恢复，还是整个方案就停了？
- raw-csi 的工作区真的能恢复吗？持续写入会怎样？
- fake IP 和 ZeroProxy 是真实网络路径，还是应用自己配合演出来的？
- 性能对比到底公平不公平？

方案可以绕开这些问题，构建不行。

我越来越觉得，AI 时代的产品经理如果仍然只交付 PRD，价值会变得很脆弱。我们不一定要变成全职工程师，但至少要有能力把关键假设推进到一个可运行、可验证、可被推翻的状态。

## 我给 Codex 的不是一个 Prompt，而是一个目标

这次最有帮助的 Codex 功能，是 `@目标`。

过去我使用 AI 工具，经常是一个问题对应一个回答：帮我写方案、解释日志、生成脚本、修改一段配置。这种方式适合局部任务，但真实项目不是一串互不相关的问题。

这个 Demo 跨了很多阶段：

1. 梳理方案边界。
2. 检查现有集群。
3. 安装和替换运行时。
4. 部署存储、网络和代理组件。
5. 恢复异常节点。
6. 跑功能、安全和性能测试。
7. 发现测试口径不对后重做。
8. 整理证据并收敛产品化方向。

中间还会遇到命令长时间运行、节点失联、环境重建、上下文切换和多轮返工。如果每一步都重新写 Prompt，AI 很容易只解决眼前的小问题，却忘了最终交付是什么。

我把这件事放进 Codex 的 `@目标` 后，体验明显不同。它不再只是回答当前一句话，而是围绕同一个目标持续推进：执行、等待、检查、失败后换路径、继续验证，直到交付条件真的满足。

当然，这不意味着我可以离开。

目标不是一句“把 Demo 做完”就够了。真正决定结果的，仍然是我不断补充和修正验收标准：普通对照必须挂载 CBS；整合组不能把组件安装时间算进 Pod 启动；网络隔离必须有普通 Pod 对照；旧的错误数据不能留在报告里；产品化不能新造一套对象，而要接入已有的 AgentWay。

Codex 很擅长沿着目标往前走，但“什么叫走对了”，仍然需要人判断。

## 第一次纠偏：不要为了组合而组合

项目最开始，我考虑把 raw-csi、Cube 和 Agent Network 放在一起。

继续梳理后，我发现这个组合不够干净。Cube 本身已经覆盖一部分运行、存储和网络能力，如果再把 raw-csi 和 Agent Network 叠上去，组件职责会重合，最后很难回答每一层到底解决什么问题。

所以我把底座改成了更直接的组合：

```text
TKE
  + gVisor
  + raw-csi
  + Agent CNI
  + ZeroProxy
```

这里每一层都可以单独解释：

- TKE 负责集群、节点池和 Kubernetes 控制面。
- gVisor 负责不可信代码的系统调用隔离。
- raw-csi 负责工作区持久化和远端恢复。
- Agent CNI 负责 fake IP、IPAM 和流量收敛。
- ZeroProxy 负责允许、拒绝、凭证注入和审计。

这个调整看起来只是技术选型，实际上是产品边界判断。

产品经理成为构建者，不是从此只听“哪个组件更先进”，而是要在真正部署之前把职责冲突拿掉。否则越努力构建，越容易得到一个无法产品化的组合。

## 从架构图进入真实集群，事情立刻变得具体

进入部署阶段以后，Codex 开始直接操作一套真实的多节点 TKE 测试集群。

它检查节点和运行时环境，安装 gVisor，部署 raw-csi 的控制器和节点插件，再把 Agent CNI 与 ZeroProxy 放到专用 Agent 节点上。

这里很快遇到了现实问题：目标节点的内核和 containerd 都比较旧，最新版 gVisor 并不能直接工作。最后只能选择兼容版本，调整 wrapper 和运行参数，再逐台验证 RuntimeClass。

随后节点又进入异常状态。

这时项目已经不再像“做一个 Demo”，而更像一次真实的小型交付：判断节点是否值得修，决定是否通过节点池删除并补充新节点，等待节点重新加入，再重新安装运行时和组件。

我授权 Codex 操作集群，它负责执行和观察；我负责决定恢复策略和可以接受的风险边界。

这个过程让我感受很深。以前在方案里写“支持节点故障恢复”，只是一行能力描述。亲手走过一次以后，才会知道它背后至少包含：节点池补充、宿主机初始化、运行时安装、DaemonSet 就绪、卷重新发布、工作区读取和网络身份重建。

产品能力不是一个名词，而是一条需要逐段成立的链路。

## Demo 跑通以后，真正困难的是证明它没有自欺欺人

最终，Claw 类 Agent 的基本链路跑通了：

- Pod 使用 gVisor 启动。
- 工作区挂载 raw-csi，并能在节点变化后恢复状态。
- Agent CNI 分配 fake IP，并把流量导向 ZeroProxy。
- 授权用户可以访问 Agent，未授权用户被拒绝。
- Agent 访问允许的 Git 目标时，由代理动态注入凭证。
- Agent 访问禁止的目标时被拒绝，并留下审计记录。

如果到这里就停止，这会是一篇很漂亮的成功故事。

但后面的性能测试让我意识到，构建者和“会跑 Demo 的人”之间还有一道门槛：是否愿意推翻对自己有利的数据。

## 两轮性能数据都被我要求作废

第一轮端到端对比看起来很糟：整合方案的 Pod 比普通 Pod 慢很多。

继续检查才发现，对照根本不公平。普通 Pod 没有挂载 CBS，而整合组却在计时期间创建 PV/PVC、初始化 NBD 和 Btrfs。测出来的不是两种 Pod 的启动差异，而是“空目录启动”对比“首次创建完整存储链路”。

这组数据没有解释价值，我要求撤回。

后来又出现了一组读写对比，同样是普通 Pod 的 `emptyDir` 对 raw-csi。它能说明两条路径不同，但不能回答 CBS 与 raw-csi 的公平差异。我再次要求把它从正式报告里删除。

最后我们重新定义测试口径：

- 普通组使用 runc、TKE 默认网络和预初始化 CBS PVC。
- 整合组使用 gVisor、Agent CNI、ZeroProxy 和预初始化 raw-csi PVC。
- 两边都提前完成卷绑定、文件系统初始化、首次挂载和镜像预热。
- 所有组件都在计时前 Ready。
- 计时只覆盖 Pod 创建到 Ready。
- 两组使用相同规格的节点，每组取得 15 个有效样本。

最终结果是：

| 指标 | 普通 Pod + CBS | 整合方案 Pod | 本次环境差异 |
| --- | ---: | ---: | ---: |
| 客户端启动平均 | 10.065 秒 | 4.946 秒 | 缩短 50.9% |
| 客户端启动 P95 | 13.090 秒 | 6.030 秒 | 缩短 53.9% |
| Kubernetes Ready 平均 | 8.067 秒 | 2.867 秒 | 缩短 64.5% |

这个结果只代表本次测试环境，不是产品 SLO，也不能直接推广到所有集群。

更重要的是，我们继续做了组件拆分。gVisor 相比 runc 的启动平均只增加约 11.8%，但 CPU 密集任务耗时约为 1.69 倍。这比一句“gVisor 性能很好”有用得多：它告诉我，启动不是主要矛盾，但 CPU 型 Coding 任务需要单独评估。

这段经历让我重新理解产品经理对数据的责任。

AI 可以很快生成测试脚本、汇总 CSV、计算 P50/P95，甚至写出一份完整报告。但如果比较对象不公平，产出越快，错误结论传播得也越快。

产品经理不能只问“数据好不好看”，而要问“这个数据到底证明了什么”。

## 一个不那么好看的 P0，反而让 Demo 更有价值

性能主测试结束后，我们继续做持续 `fsync` 写入。

raw-csi 的 NBD 数据路径出现超时，Btrfs 被强制切成只读。更麻烦的是，Kubernetes 里的 Pod 仍然显示 Running/Ready，挂载信息看起来也可能还是可写，但实际写入已经失败。

这意味着当前系统不仅会发生存储故障，还不能把故障状态准确传递给上层。

这个问题被定为 P0：在修复 NBD 超时、只读检测和自动恢复之前，整套方案只能算可运行 Demo，不能宣称生产可用。

坦白说，这不是一个适合放在“成果汇报”里的结论。

但它恰恰是构建的价值。

如果只做方案，我可能会写“支持持久化和故障恢复”。如果只跑短链路 Demo，我也可能会认为这项能力已经验证。只有继续施压，才会看到系统在失效时如何撒谎：底层已经只读，上层仍然绿色。

产品经理亲自走到这里，对 Day 2 运维的理解会完全不同。监控、健康传播、自愈、灰度和回滚不再是路线图里的标准词汇，而是决定客户敢不敢用的产品本体。

## AI 做了很多，但产品判断没有被外包

这次项目里，Codex 做了大量过去需要工程同学持续投入的工作：

- 阅读仓库和部署清单。
- 检查集群、节点、Pod 和事件。
- 修改运行时安装脚本。
- 部署和重建组件。
- 等待长时间任务并继续处理结果。
- 编写性能测试与结果分析脚本。
- 收集日志、内核信息和 Kubernetes 状态。
- 更新文档和归档证据。
- 清理已经作废的数据。

但真正改变项目方向的几次动作，仍然来自人的判断：

- 发现 Cube 与现有存储、网络能力重叠，改变技术组合。
- 明确项目与其他无关产品没有关系，阻止范围漂移。
- 要求交付 Coding Agent 和 Claw Agent 这类真实 Use Case。
- 发现性能对照不公平，连续撤回两轮数据。
- 要求普通 Pod 必须挂载 CBS，整合组必须提前准备好全部组件。
- 不因为启动数据好看就忽略 raw-csi 的 P0。
- 产品化时放弃 Demo 自定义对象，改为接入已有 AgentWay 的 Agent、AgentTemplate 和 Provider 体系。

所以我不认为 AI 把产品经理变成了工程师。

更准确的说法是：AI 把产品经理的判断半径扩大了。过去一个判断可能停留在文档里，现在它可以快速变成脚本、资源、测试和证据；错误判断也会更快暴露。

## 为什么 `@目标` 对这种项目特别有用

回头看，这个项目并不是靠某个神奇 Prompt 完成的。

真正有用的是把长期任务组织成一个持续目标，然后在过程中不断修正它。

我使用 Codex `@目标` 时，最明显的几个价值是：

### 1. 它保留的是交付目标，不只是当前问题

节点恢复不是终点，恢复后还要重新部署；重新部署不是终点，还要跑验证；验证通过也不是终点，还要补公平对照和归档。

目标让这些步骤属于同一件事。

### 2. 它适合基础设施任务里的等待和反复

节点创建、Pod rollout、卷挂载、长时间测试都不会在一次对话里瞬间结束。Codex 可以持续观察任务，在命令结束后接着处理，而不是每次都让我重新解释上下文。

### 3. 它允许人随时改变验收标准

我不是一开始就把所有测试条件都写对了。很多要求是在看到结果后才补上的。目标并没有把项目锁死在第一版计划里，我可以继续说“这组不公平，重做”“旧数据全部删除”“产品化改为基于 AgentWay”，然后让执行路径随之改变。

### 4. 它把“完成”变成可以审计的状态

对我来说，完成不是 Codex 回一句“已部署”，而是集群状态、测试结果、失败证据、文档和可复现资产都能对上。`@目标` 最有价值的地方，是让 AI 围绕这个完成定义持续工作。

当然，目标模式也更需要人保持清醒。任务越长，越容易出现局部成功被误认为整体成功、旧结论没有清理、范围悄悄漂移等问题。AI 能持续推进，人就更要持续校准。

## 从 Demo 到产品，最后一次收敛仍然是产品判断

Demo 过程中，为了快速声明 Runtime、Workspace 和 Network，我们做过一个自定义对象。

但到了产品化设计阶段，我认为不应该把 Demo 的临时抽象直接升级成新产品 API。团队本身已经有 AgentWay，具备 AgentTemplate、Agent、AgentInfraProvider、Console 和 Operator。

更合理的产品路径，是把这套 TKE Runtime 能力做成 AgentWay 的 Provider：

```text
AgentWay Agent
  -> AgentTemplate
  -> AgentInfraProvider/tke-runtime
  -> gVisor + Workspace + Agent Network
```

这样用户继续使用已有的 Agent 创建、暂停、恢复、重启和状态体系，底层 Provider 再把意图转换成 Pod、PVC、网络策略和代理配置。

这一步没有增加 Demo 的功能，却让产品边界清楚了很多。

构建者不是永远增加东西。有时亲手做过以后，最重要的决定是知道什么不应该成为产品。

## 我理解的“产品经理转型成构建者”

做完这次实践，我不再把“构建者”理解成会写多少代码。

对产品经理来说，它更像四种能力的组合。

第一，**把模糊判断变成可验证假设**。

不是说“Agent 需要更安全的环境”，而是定义：未授权目标必须被拒绝，凭证不能进入容器，节点变化后工作区要能恢复。

第二，**能把 AI 调度到真实交付链路里**。

不是让 AI 写一段示例代码，而是让它读环境、执行、等待、验证、处理失败和整理证据。

第三，**对测试口径和证据负责**。

看到漂亮数据时先检查对照，看到绿色状态时继续检查真实可用性，发现错误结论后愿意删除，而不是加一段注释继续保留。

第四，**能从技术结果重新做产品收敛**。

Demo 不是为了证明最初方案永远正确，而是为了帮助我们改变方案：哪些组件应该替换，哪些风险必须变成 P0，哪些临时对象不该进入产品。

## 最后

这套 Agent Runtime 还不是生产产品。

它已经证明了 gVisor、持久工作区、fake IP 和 ZeroProxy 可以形成一条完整链路，也在一次受控环境里取得了不错的启动结果。但 raw-csi 的持续写稳定性、现代内核兼容、健康传播和自动恢复仍然需要继续解决。

对我个人来说，更重要的结果不是 Demo 本身。

而是我开始形成一种新的工作方式：产品经理不再只把问题交给工程团队，然后等待“实现反馈”；我可以借助 Codex，把关键假设推进到真实环境里，让系统用日志、性能和故障回答我。

AI 工具没有替我做产品判断。

它让我不得不更认真地做判断，因为每一个判断都可以更快地被构建出来，也更快地被现实推翻。

这可能就是我现在理解的构建者：

> 不只是提出一个看起来正确的方向，而是愿意和 AI 一起把它跑起来、测清楚、承认失败，再把真正成立的部分做成产品。
