# 给 Codex 接上长期记忆：一次 Obsidian + 插件的实践

这次折腾的起点，是一个我在用 Codex 时越来越明显的问题：

> 很多真正有价值的上下文，不属于某一个项目。

比如我在不同会话里做过 raw-csi 的能力表达，做过 Cube / Sandbox / Agent Runtime 的方案讨论，也做过 Agent Network 的 demo 和产品化拆解。单独看，每个会话都有自己的产物；但真正做产品规划或者组合 demo 时，我需要的不是“当前仓库上下文”，而是这些项目之间的长期记忆。

问题是，Codex 的会话天然是短期的。一个任务做完，信息留在了那次对话里；换一个项目、换一个线程，很多决策、偏好、证据又要重新解释一遍。

所以这次我想试一个更朴素的方案：把 Obsidian 当成 Codex 的跨项目长期记忆库，再用 Codex 插件把“什么时候读、读多少、什么时候写回”这件事固定下来。

## 🤔 一开始想解决什么

我最初的诉求不是“做一个知识库”。

知识库这个词太大了，也容易把事情做复杂。真正困扰我的是几个更具体的场景：

- 做产品规划时，需要知道多个项目以前为什么这么设计。
- 做 demo 整合时，需要把 raw-csi、Cube、Agent Network 这类项目的能力重新组合。
- 做复盘或写方案时，不想每次都重新解释我的偏好、工作流和长期主线。
- 某些决策已经讨论过，不希望未来又在另一个会话里从头纠结。

也就是说，我需要的不是“所有内容都永久保存”，而是 **稳定知识能跨会话复用**。

这里的稳定知识包括几类：事实、决策、能力、证据。比如某个项目已经验证过什么，某个方案为什么被选中，某个 demo 的边界在哪里，某个文章或 PRD 放在哪个路径。

这些东西如果能被 Codex 在新任务里重新召回，就会省掉大量重复沟通。

## 🧱 第一版：先把 Obsidian Vault 搭起来

第一步很简单：建一个专门给 Codex 用的 Obsidian vault。

结构大概是这样：

```text
Obsidian-Codex-Memory/
  CODEX_README.md
  00-Codex-入口/
  10-长期规划/
  20-偏好与原则/
  30-工作流/
  40-决策日志/
  50-项目记忆/
  90-Inbox/
  templates/
```

我没有把它设计成一个很重的知识管理系统。每个目录只承担一个清楚的角色：

- `00-Codex-入口`：告诉 Codex 进来以后先读什么、怎么判断要不要深度召回。
- `10-长期规划`：保存长期主线，不让短期任务完全失焦。
- `20-偏好与原则`：保存我对工作方式、输出质量、证据边界的偏好。
- `30-工作流`：保存可复用流程，比如记忆写入、跨项目任务处理。
- `40-决策日志`：记录重要选择及其原因。
- `50-项目记忆`：按项目保存稳定事实、能力和证据。
- `90-Inbox`：放每日沉淀和暂时不确定、但可能有用的信息。

这个结构的重点不是“分类优雅”，而是让 Codex 能够快速找到入口，不需要每次从一堆散乱笔记里猜。

## 🔁 第二步：每天 11:30 自动沉淀

长期记忆如果全靠手动维护，很快就会断掉。

所以我又配置了一个 Codex 自动化：每天上午 11:30，把最近的 Codex 沟通记录做一次稳定信息沉淀，写进 Obsidian。

但这里有一个很重要的边界：自动化不负责写“聪明总结”。

它只沉淀四类东西：

| 类型 | 写什么 |
| --- | --- |
| 事实 | 发生了什么，产物在哪里，验证到什么程度 |
| 决策 | 做了什么选择，为什么，适用范围是什么 |
| 能力 | 某个项目稳定贡献什么能力，边界是什么 |
| 证据 | 文档、原型、PRD、验证结果、提交、报告的位置 |

它不搬运原始聊天，不写未经验证的猜测，也不提前帮未来维护“场景包”。

这一点是后来反复调整才定下来的。

一开始我也想过按场景维护记忆包，比如“产品规划包”“demo 整合包”“Agent 基础设施包”。但很快发现这会把维护成本推高：每次新项目、新证据、新组合方式出现，都要想这个信息应该放进哪个包。

更麻烦的是，这会把“未来怎么用”的要求提前塞进“现在怎么归档”里。长期看一定会难维护。

所以最后改成了一个更干净的原则：

> 归档只负责准确保存。使用时再按任务目标精确召回。

## 🧭 关键转折：归档逻辑和使用逻辑分开

这可能是整个方案里最重要的设计。

我把系统拆成两层：

```text
归档层：存准、存稳、可检索、可引用
使用层：任务发生时再检索、组合、判断、验证
```

归档层不关心未来会不会把 raw-csi 和 Cube 组合，不提前写“未来 demo 方案”，也不维护跨项目场景包。它只记录每个项目已经确认的能力、边界和证据。

使用层则在具体任务发生时工作。比如我说：

> 把 raw-csi、Cube、agent network 结合成一个 demo。

这时候 Codex 再去搜索这几个项目，读取相关能力和证据，临时组合出本次任务所需的上下文包。

这个分离让我很舒服。因为它保留了 Obsidian 作为长期记忆库的稳定性，也保留了 Codex 在具体任务里做上下文组合的灵活性。

## 🔌 第三步：做成 Codex 插件

光有 Obsidian 目录还不够。

如果每次都要我手动告诉 Codex：“去读这个目录、先看这个文件、再检索那些项目”，那长期也会很累。

所以后面把这套规则做成了一个 Codex 插件：`obsidian-memory`。

插件里拆了三个 skill：

```text
obsidian-memory-lite
obsidian-memory-deep
obsidian-memory-archive
```

它们的分工很清楚。

### Lite：默认少量召回

`obsidian-memory-lite` 适合普通任务开始前做轻量定向。

它只读入口文件、偏好、长期主线，然后用 3 到 6 个关键词在 vault 里找最相关的 1 到 3 个文件。它的目标是低 token、快启动，帮助 Codex 不至于完全失忆。

它不全量扫描 vault，也不读所有 Inbox。

### Deep：复杂任务深度召回

`obsidian-memory-deep` 用在需要全局上下文的任务里。

比如产品规划、跨项目 demo、多个项目能力整合，或者我明确说“深度召回 Obsidian 记忆”。

这个模式不太在乎 token 消耗，重点是准确。它会围绕项目名、能力词、意图词反复搜索，比如 `raw-csi`、`Cube`、`Agent Network`、`storage`、`checkpoint`、`runtime`、`network`、`demo`、`证据` 等。

这里我最后没有把检索交给一个 ranking 脚本。

原因也很现实：深度召回的场景里，我更在乎准确性，而不是省 token。检索脚本可以帮助粗筛，但它很难理解“这条笔记对当前任务是不是真的有用”。所以最终方案是让 Codex 直接用 `rg` 迭代搜索、读文件、交叉判断，再临时生成上下文包。

### Archive：只写稳定知识

`obsidian-memory-archive` 则只负责写回。

它不会把临时方案、未经确认的推理、原始聊天塞进 Obsidian。只有当任务产生了新的事实、决策、能力或证据时，才回写到对应目录。

这个边界很重要。否则记忆库很快就会变成另一个杂乱聊天记录仓库。

## ✅ 实际做出来的效果

这次最后形成了几件真实可用的东西。

第一，Obsidian vault 已经能作为跨项目记忆入口使用。

新会话只要读取入口文件，就能知道长期主线、工作偏好、写入边界、跨项目检索规则和项目记忆位置。

第二，每日沉淀自动化已经建立。

它会每天 11:30 把 Codex 沟通记录中的稳定信息沉淀进 Obsidian。当天也做了一次手动试跑，生成了 dated archive，能看到它会记录读取范围、更新文件、沉淀出的长期记忆条目、被跳过的信息和待确认项。

第三，跨项目读取做过验证。

我在 raw-csi 项目下新开了一个 Codex 任务，让它读取这个 Obsidian vault。测试结果是：只要给出明确路径，新任务可以跨项目读到入口、偏好和 raw-csi 项目记忆。

这个验证有边界：它证明了跨项目文件读取可行，但还不能证明所有普通任务都会自动主动读取。所以后面才需要插件来把这件事产品化。

第四，`obsidian-memory` 插件已经安装并启用。

它不是一个复杂插件，没有服务端，也没有数据库。它更像是一套固定工作法：默认轻量召回，复杂任务深度召回，需要沉淀时再稳定归档。

## 🧩 我现在怎么理解这套系统

这套系统不是为了让 Codex “记住所有东西”。

恰恰相反，它是在给记忆做边界。

很多会话内容其实不值得永久保存：临时命令、工具输出、还没确认的猜测、过程中的废案。如果全都进长期记忆，未来召回时反而会污染判断。

真正应该留下来的，是那些未来还会影响决策的东西：

- 我为什么选择某条路线。
- 某个项目已经验证过什么。
- 某个能力的边界在哪里。
- 哪些材料可以作为证据。
- 我对工作流和输出质量有什么稳定偏好。

也因此，这套系统的核心不是 Obsidian，也不是插件，而是一个原则：

> 长期记忆保存稳定事实，任务现场负责重新组合。

这和人的工作方式其实挺像。我们不会把每一次闲聊都当成知识，但会记住关键判断、证据和路径。真正做事时，再根据当前问题把这些记忆拿出来重新组织。

## 🤔 这次踩到的几个点

第一个点是，不要一开始就做“智能归档”。

听起来越智能，越容易把未来使用场景写死。归档层应该朴素一点，只保证信息真实、稳定、可检索。

第二个点是，轻量召回和深度召回要分开。

如果每次任务都全量读 Obsidian，token 会爆炸，也会让上下文变脏。但如果只读当前项目，又违背了跨项目永久记忆的初衷。所以更合理的方式是：默认少量召回，必要时手动切深度召回。

第三个点是，深度召回不要过度依赖脚本。

脚本适合找词，不适合判断“这条信息对当前产品方案是否关键”。复杂任务里，Codex 直接读足够多的相关笔记，再做人工式筛选，反而更符合我的目标。

第四个点是，记忆库也需要“拒绝写入”。

不是所有东西都要保存。尤其是未经验证的推测、内部敏感链接、原始长聊天、临时日志，这些东西进入长期记忆之后，未来很可能变成噪音甚至风险。

## 📊 这次产物

| 产物 | 作用 |
| --- | --- |
| Obsidian vault | Codex 跨项目长期记忆库 |
| 启动入口 | 告诉 Codex 先读什么、怎么理解记忆边界 |
| 归档与使用分离原则 | 防止把未来召回逻辑塞进归档逻辑 |
| 每日 11:30 自动化 | 定期把稳定沟通记录沉淀到 Obsidian |
| obsidian-memory-lite | 普通任务的低 token 轻量召回 |
| obsidian-memory-deep | 产品规划和跨项目整合时的高准确召回 |
| obsidian-memory-archive | 只把稳定事实、决策、能力和证据写回 |

## 💭 总结

这次做完以后，我感觉 Codex 更像是有了一个“长期工作台”。

它不再只是单个会话里的执行助手，而是可以在多个项目之间带着一些稳定记忆移动：知道我偏好的表达方式，知道哪些项目有过哪些能力验证，也知道什么时候应该查证，而不是直接相信旧笔记。

当然，这还只是第一版。

后面真正要验证的是：当我做一个复杂产品规划，或者把 raw-csi、Cube、Agent Network 组合成新 demo 时，这套记忆系统能不能减少重复解释，能不能召回足够准确的证据，能不能避免把旧结论误当成当前事实。

如果它能做到这一点，那 Obsidian 就不只是一个笔记库，而会变成 Codex 跨项目协作里的长期上下文层。
